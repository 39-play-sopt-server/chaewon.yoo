# 6주차 키워드 과제

## 1. 세션 기반 인증

세션 기반 인증은 서버가 로그인한 사용자의 인증 정보를 저장하고, 클라이언트는 세션 ID를 전달해 자신을 확인받는 방식이다. HTTP는 이전 요청을 기억하지 않으므로 세션을 이용해 여러 요청에서 로그인 상태를 유지한다.

| 구분 | 역할 |
| --- | --- |
| 클라이언트 | 로그인 정보를 전송하고, 이후 요청에 세션 ID가 담긴 쿠키를 보낸다. |
| 서버 | 로그인 정보를 검증하고, 세션에 저장한 인증 정보를 이용해 요청을 처리한다. |
| 세션 ID | 서버에 저장된 세션을 찾기 위한 식별자이다. |

### 로그인 요청과 세션 생성

1. 사용자가 이메일과 비밀번호를 입력하면 클라이언트가 HTTPS로 로그인 요청을 보낸다.
2. 서버는 회원을 조회하고 입력한 비밀번호를 저장된 비밀번호 해시와 비교한다. 비밀번호는 복호화해서 비교하는 것이 아니라 비밀번호 검증 함수를 사용한다.
3. 인증에 성공하면 서버는 세션에 사용자 식별자 등의 인증 정보를 저장한다. 로그인 전에 세션이 있었다면 세션 고정 공격을 막기 위해 세션 ID를 변경한다.
4. 서버는 `Set-Cookie` 응답 헤더로 세션 ID를 전달한다. Java 웹 애플리케이션에서는 일반적으로 `JSESSIONID`라는 이름을 사용한다.
5. 브라우저는 쿠키를 저장하고, 쿠키의 도메인과 경로 등의 조건에 맞는 이후 요청에 함께 보낸다.

클라이언트에 전달하는 것은 세션 ID이며, 서버에 저장한 사용자 정보 전체를 쿠키에 담는 것은 아니다.

### 이후 요청의 검증

1. 브라우저가 세션 ID를 `Cookie` 헤더에 담아 요청한다.
2. 서버는 해당 ID로 세션을 찾고 만료되었거나 무효화된 세션인지 확인한다.
3. 유효한 세션에 인증 정보가 있으면 로그인한 사용자로 처리한다.
4. 요청한 기능을 사용할 권한이 있는지 확인한 뒤 비즈니스 로직을 실행한다.

인증은 누구인지 확인하는 과정이고, 인가는 해당 사용자가 요청한 작업을 해도 되는지 확인하는 과정이다. API에서 인증 정보가 없거나 유효하지 않으면 보통 `401`, 인증은 되었지만 권한이 없으면 `403`으로 응답한다. 화면을 제공하는 서비스에서는 로그인 화면으로 이동시킬 수도 있다.

### 로그아웃과 주의할 점

로그아웃하면 서버의 세션을 무효화하고 클라이언트의 세션 쿠키도 만료시킨다. 쿠키만 삭제하면 서버의 세션이 남을 수 있으므로 서버에서도 로그인 상태를 종료해야 한다.

세션 쿠키에는 HTTPS에서만 전송하는 `Secure`, JavaScript로 읽지 못하게 하는 `HttpOnly`, 다른 사이트에서 시작된 요청의 쿠키 전송을 제한하는 `SameSite` 설정을 사용할 수 있다. 쿠키가 자동 전송되는 인증 방식이므로 상태를 변경하는 요청에는 CSRF 대응도 필요하다.

서버가 여러 대라면 어느 서버에서 요청을 받더라도 같은 세션을 확인할 수 있도록 공유 저장소 등을 고려해야 한다. 로그인 상태를 서버에서 직접 종료하기는 쉽지만, 사용자가 늘어나면 세션을 저장하고 관리하는 비용도 늘어난다.

## 2. 토큰 기반 인증

토큰 기반 인증은 로그인에 성공한 사용자에게 토큰을 발급하고, 이후 요청에서 전달된 토큰을 검증하는 방식이다. JWT는 토큰에 필요한 정보를 담는 형식 중 하나이며, 모든 토큰이 JWT인 것은 아니다.

### JWT의 구조

일반적으로 사용하는 서명된 JWT는 `Header.Payload.Signature` 형태이다.

| 구성 | 의미 |
| --- | --- |
| Header | 토큰 유형과 서명 알고리즘 등의 정보를 담는다. |
| Payload | 사용자 식별자와 만료 시각 등의 claim을 담는다. |
| Signature | 토큰이 변경되지 않았는지 검증하는 데 사용한다. |

claim은 토큰이 전달하는 정보이다. `sub`는 대상 사용자, `exp`는 만료 시각, `iat`는 발급 시각, `iss`는 발급자, `aud`는 사용 대상을 나타낸다. `jti`는 토큰 식별자로 사용할 수 있다. 실제 검증할 항목은 서비스가 정한 규칙에 맞춰 구성한다.

서명된 JWT의 Header와 Payload는 인코딩된 값이므로 읽을 수 있다. 서명은 암호화와 다르며, 비밀번호나 외부에 공개하면 안 되는 정보를 Payload에 담으면 안 된다.

### 로그인 요청과 토큰 발급

1. 클라이언트가 이메일과 비밀번호로 로그인 요청을 보낸다.
2. 서버는 회원 정보와 비밀번호를 검증한다.
3. 인증에 성공하면 사용자 식별자, 만료 시각 등을 담아 Access Token을 발급한다. 재발급 기능이 있다면 Refresh Token도 함께 발급한다.
4. 서버는 정해진 응답 방식으로 토큰을 전달한다. Access Token은 응답 본문이나 헤더로 전달할 수 있고, Refresh Token은 `HttpOnly` 쿠키에 담는 방식을 사용할 수 있다.
5. 클라이언트는 이후 API 요청에 Access Token을 포함한다. 일반적으로 `Authorization: Bearer <Access Token>` 형식을 사용한다.

| 구분 | Access Token | Refresh Token |
| --- | --- | --- |
| 목적 | 보호된 API에 접근한다. | 새로운 Access Token을 발급받는다. |
| 유효기간 | 비교적 짧게 설정한다. | 보통 Access Token보다 길게 설정한다. |
| 사용 범위 | 인증이 필요한 API 요청에 사용한다. | 토큰 재발급 요청에 사용한다. |

두 토큰은 목적이 다르므로 Refresh Token으로 일반 API에 접근하거나 Access Token으로 재발급받지 못하도록 구분해서 검증해야 한다. Refresh Token은 반드시 JWT여야 하는 것은 아니다.

### 이후 요청의 검증

1. 서버는 요청 헤더에서 Access Token을 추출한다.
2. 허용한 알고리즘과 서버가 신뢰하는 키로 서명을 검증한다. 토큰이 지정한 알고리즘을 그대로 믿고 처리하지 않는다.
3. 만료 시각과 필요한 claim을 확인한다. 발급자, 사용 대상, 토큰 용도 등도 서비스의 검증 규칙에 따라 확인한다.
4. 검증에 성공하면 사용자 식별자를 이용해 인증 정보를 구성한다. 무효화 저장소를 사용한다면 해당 토큰이 아직 유효한지도 확인한다.
5. 요청에 필요한 권한과 자원의 소유 여부 등을 확인하고 기능을 실행한다.

JWT의 내용을 디코딩하는 것만으로 인증이 끝나는 것은 아니다. 서명과 claim을 검증하기 전에 읽은 값을 신뢰하면 안 된다.

### Access Token 재발급

1. Access Token이 만료되어 API 요청이 `401`로 실패하면 클라이언트가 재발급을 요청한다.
2. 서버는 Refresh Token의 유효성과 용도를 확인한다. 저장소에서 관리한다면 등록 여부와 만료·폐기 여부도 확인한다.
3. 유효한 Refresh Token이면 새로운 Access Token을 발급한다. Refresh Token도 교체하는 정책이라면 기존 토큰을 폐기하고 새 토큰을 전달한다.
4. 클라이언트는 새 Access Token으로 원래 요청을 다시 보낸다.
5. Refresh Token까지 만료되거나 무효화되었다면 다시 로그인해야 한다.

Refresh Token을 쿠키로 전달하면 브라우저가 자동으로 전송하므로 재발급 요청에도 CSRF 대응이 필요하다. `HttpOnly`는 JavaScript가 쿠키를 읽는 것을 막지만, XSS로 사용자의 브라우저에서 요청이 실행되는 것까지 막지는 못한다.

JWT는 서명 검증만으로 확인할 수 있지만, 로그아웃했다고 이미 발급한 토큰이 자동으로 무효화되지는 않는다. 즉시 차단하려면 허용된 토큰을 관리하는 화이트리스트나 폐기된 토큰을 관리하는 블랙리스트 등을 사용할 수 있다. 이 경우에는 토큰 방식이라도 서버에서 상태를 관리하게 된다.

## 3. OAuth의 인증 프로세스

OAuth 2.0은 사용자의 비밀번호를 외부 서비스에 직접 전달하지 않고, 정해진 범위의 자원 접근 권한을 위임하는 표준이다. OAuth 자체는 인가를 위한 것이며, 소셜 로그인에서 사용자 인증을 표준화한 방식은 OAuth 2.0 위에 인증 기능을 추가한 OpenID Connect이다.

### 참여자의 역할

| 구분 | 역할 |
| --- | --- |
| 사용자와 브라우저 | 소셜 로그인을 시작하고, 제공자 화면에서 로그인과 동의를 진행한다. |
| 서비스 서버 | OAuth 클라이언트로서 인가 요청을 시작하고, 인가 코드를 토큰으로 교환한 뒤 서비스의 회원을 연결한다. |
| 인가 서버 | 사용자를 인증하고 동의를 확인한 뒤 인가 코드와 토큰을 발급한다. |
| 자원 서버 | 제공자가 발급한 Access Token을 확인하고 허용된 사용자 정보 등의 자원을 반환한다. |

프론트엔드를 클라이언트라고 부르기도 하지만, OAuth에서의 클라이언트는 제공자에게 자원 접근 권한을 요청하는 애플리케이션을 뜻한다. 서버가 인가 코드를 교환하는 구조에서는 서비스 서버가 이 역할을 수행한다.

### 인가 코드 방식의 로그인 흐름

1. 사용자가 소셜 로그인 버튼을 누르면 브라우저가 서비스 서버의 로그인 시작 경로로 이동한다.
2. 서비스 서버는 브라우저를 제공자의 인가 화면으로 보낸다. 이때 `client_id`, 등록된 `redirect_uri`, 요청 권한인 `scope`, 요청과 응답을 연결하는 `state` 등을 전달한다. OpenID Connect에서는 `openid` scope와 재사용 공격 방지를 위한 `nonce`도 사용할 수 있다.
3. 제공자는 자신의 화면에서 사용자를 로그인시키고 필요한 권한에 대한 동의를 받는다. 사용자의 소셜 계정 비밀번호는 서비스 서버가 직접 받지 않는다.
4. 제공자는 브라우저를 등록된 콜백 주소로 이동시키며 짧은 수명의 인가 코드와 `state`를 전달한다.
5. 서비스 서버는 `state`가 처음 요청할 때 저장한 값과 일치하는지 확인한다. 이후 인가 코드와 필요한 클라이언트 인증 정보를 제공자의 토큰 엔드포인트로 전송한다. PKCE를 사용했다면 처음 보낸 challenge에 대응하는 verifier도 전달한다.
6. 제공자는 코드를 검증하고 Access Token을 발급한다. OpenID Connect에서는 사용자 인증 결과가 담긴 ID Token도 전달한다.
7. 서비스 서버는 ID Token의 서명, 발급자, 사용 대상, 만료 시각 등을 확인하고 `nonce`를 보냈다면 일치 여부도 확인한다. 추가 사용자 정보가 필요하면 제공자의 Access Token으로 UserInfo API를 호출할 수 있다.
8. 확인한 제공자 종류와 사용자 식별자(`sub`)로 기존 회원을 찾거나 가입 절차를 진행한다.
9. 서비스 서버는 자신의 세션이나 서비스용 토큰을 발급하고, 이후 요청은 서비스의 인증 방식으로 처리한다.

인가 코드는 API 접근에 사용하는 Access Token과 다르다. 브라우저를 거쳐 전달된 코드를 서버가 토큰으로 교환하며, 코드는 짧게 유효하고 한 번만 사용할 수 있어야 한다.

### 토큰과 계정 연결 시 주의할 점

제공자의 Access Token은 제공자의 API를 호출하기 위한 것이고, ID Token은 사용자 인증 결과를 확인하기 위한 것이다. 서비스가 발급한 Access Token은 서비스 API에 접근하기 위한 것이므로 서로 같은 용도로 사용하면 안 된다.

`client_id`는 애플리케이션 식별자이고, `client_secret`은 서버가 안전하게 보관해야 하는 인증 정보이다. 브라우저에 노출되는 코드나 공개 저장소에 secret을 넣으면 안 된다. `state`는 로그인 요청과 콜백을 연결하는 데 사용하고, PKCE는 가로챈 인가 코드만으로 토큰을 발급받기 어렵게 한다.

이메일이 같다는 이유만으로 일반 회원과 소셜 회원을 자동 연결하면 계정 소유 여부를 잘못 판단할 수 있다. 제공자와 사용자 식별자를 기준으로 구분하고, 계정을 연결하려면 기존 계정에 대한 별도의 인증 절차를 고려해야 한다.
