# 2주차 키워드 과제

## 1. Java의 record

record는 데이터를 묶어서 전달하기 위한 클래스이다. 필드를 선언하면 생성자와 접근자 및 equals(), hashCode(), toString()을 자동으로 만든다.

| 구분 | 일반 클래스 | record |
| --- | --- | --- |
| 필드 | 변경 가능 여부를 직접 정한다. | 선언한 데이터 필드는 final이다. |
| 생성자와 접근자 | 직접 작성할 수 있다. | 기본 형태가 자동 생성된다. |
| 상속 | 조건에 따라 다른 클래스를 상속할 수 있다. | 다른 클래스를 상속하거나 record를 상속할 수 없다. |
| 사용 상황 | 상태와 동작을 함께 관리한다. | 요청과 응답 같은 데이터를 전달한다. |

현재 CreatePostRequest와 PostResponse에 사용하고 있다. 접근자는 getTitle() 대신 title()처럼 호출한다. 조회수처럼 상태가 바뀌는 Post는 일반 클래스로 구현했다.

record가 가진 참조를 바꿀 수는 없지만 내부에 담긴 List 등의 내용까지 불변이 되는 것은 아니다.

## 2. @Controller와 @RestController

두 어노테이션은 HTTP 요청을 처리하는 클래스를 Spring에 알리는 역할이다. 차이는 반환값을 처리하는 방식이다.

| 구분 | @Controller | @RestController |
| --- | --- | --- |
| 기본 반환 처리 | 화면 이름 등을 해석해 뷰를 반환한다. | 반환값을 응답 본문에 담는다. |
| 사용 상황 | HTML 화면을 제공한다. | JSON 등의 데이터를 제공한다. |
| 데이터 응답 | @ResponseBody를 붙여 처리할 수 있다. | @ResponseBody가 포함되어 있다. |

@RestController는 @Controller와 @ResponseBody를 결합한 어노테이션이다. 현재 PostController는 게시글 데이터를 JSON으로 반환하므로 @RestController를 사용한다.

## 3. DTO / VO / DAO

| 구분 | 의미 | 필요한 이유 | 사용 상황 |
| --- | --- | --- | --- |
| DTO | 계층 사이에서 데이터를 전달하는 객체이다. | 외부 요청과 응답을 내부 도메인 구조와 분리한다. | API 요청과 응답 데이터를 전달한다. |
| VO | 값 자체로 의미와 동일성을 표현하는 객체이다. | 값에 관한 규칙을 한곳에 모은다. | 금액이나 이메일 같은 값을 표현한다. |
| DAO | 저장소에 접근하는 객체이다. | 저장 기술과 데이터 접근 코드를 분리한다. | 데이터를 저장하거나 조회한다. |

현재 CreatePostRequest와 PostResponse는 DTO이다. 게시글 객체를 그대로 반환하지 않고 필요한 데이터를 전달한다.

VO는 객체의 식별자보다 값을 기준으로 비교한다. 같은 금액을 나타내는 두 Money 객체는 같은 값으로 볼 수 있다. 보통 불변으로 설계하고 생성 시 값의 규칙을 검증한다. record로 구현할 수 있지만 모든 record가 VO인 것은 아니다.

DAO는 데이터 접근을 맡으며 SQL 같은 저장소 관련 코드를 다른 계층에서 분리한다. 현재 프로젝트에서는 PostRepository가 메모리 저장소 접근을 맡고 있다.

## 4. RESTful이란?

RESTful은 REST의 제약을 따르도록 설계한 시스템을 뜻한다. REST는 자원을 표현하고 그 표현을 통해 클라이언트와 서버가 통신하는 아키텍처 스타일이다.

| 제약 | 의미 |
| --- | --- |
| 클라이언트와 서버 분리 | 화면 처리와 서버의 역할을 나눈다. |
| 무상태 | 각 요청에 처리에 필요한 정보를 담는다. |
| 캐시 | 응답을 재사용할 수 있는지 알려준다. |
| 일관된 인터페이스 | 자원과 요청을 공통 규칙으로 표현한다. |
| 계층 구조 | 중간 서버가 있어도 클라이언트가 내부 구조를 알 필요가 없다. |

일관된 인터페이스에는 자원 식별과 표현을 통한 조작이 포함된다. 메시지만으로 요청과 응답을 이해할 수 있어야 한다. 응답의 링크를 통해 다음 동작을 안내하는 하이퍼미디어도 포함된다. 서버가 실행 코드를 전달하는 Code on Demand는 선택 제약이다.

현재 과제는 /api/v1/posts로 자원을 표현한다. GET은 조회에 사용하고 POST는 생성에 사용한다. PUT과 DELETE로 수정과 삭제를 구분한다. 상태 코드와 공통 응답으로 처리 결과를 전달한다. 하이퍼미디어는 구현하지 않았다.

RESTful은 클라이언트와 서버가 서로의 내부 구현을 몰라도 자원과 메시지를 이해할 수 있도록 만드는 설계라고 생각한다. URL뿐 아니라 메서드와 상태 코드 및 응답 표현을 함께 고려해야 한다.

## 5. Spring Bean의 생명주기

Bean은 Spring 컨테이너가 생성하고 관리하는 객체이다. 생명주기는 객체를 준비해서 사용하고 종료 시 필요한 자원을 정리하는 과정이다.

일반적인 싱글톤 Bean의 흐름은 다음과 같다.

| 단계 | 의미와 특징 |
| --- | --- |
| Bean 정의 등록 | 어떤 객체를 만들고 어떻게 연결할지 등록한다. |
| 객체 생성과 의존성 주입 | 객체를 만들고 필요한 다른 Bean을 연결한다. 생성자 주입은 객체 생성 과정에서 이루어진다. |
| 초기화 | 의존성이 연결된 뒤 사용 준비를 한다. 필요한 경우 @PostConstruct 등을 사용한다. |
| 사용 | 준비된 Bean이 요청을 처리한다. |
| 소멸 | 컨테이너가 종료되면 정리 작업을 수행한다. 필요한 경우 @PreDestroy 등을 사용한다. |

초기화 전후에는 BeanPostProcessor가 추가 처리를 할 수 있다. 이 과정에서 기능을 덧붙인 프록시 객체가 만들어지기도 한다.

현재 PostService는 @Service로 등록된 Bean이다. Spring이 PostRepository를 생성자에 전달해서 연결한다. 게시글인 Post는 직접 new로 생성하는 객체이므로 Bean이 아니다.
