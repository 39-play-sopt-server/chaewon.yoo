# 4주차 키워드 과제

## 1. CI/CD

CI/CD는 코드 변경을 통합하고 검증한 뒤 배포까지 이어지는 과정을 자동화하는 방식이다. 테스트와 빌드를 반복해서 실행하므로 통합 과정의 문제를 일찍 발견하고, 배포할 때마다 같은 절차를 적용할 수 있다.

| 구분 | 의미 | 동작 예시 |
| --- | --- | --- |
| CI (Continuous Integration) | 지속적 통합 | PR을 열거나 커밋을 푸시하면 빌드와 테스트를 실행한다. |
| CD (Continuous Delivery) | 지속적 제공 | 검증을 통과한 변경을 배포 가능한 상태로 준비하고, 운영 배포에는 수동 승인 단계를 둘 수 있다. |
| CD (Continuous Deployment) | 지속적 배포 | 정해진 검증을 통과한 변경을 운영 환경에 자동으로 배포한다. |

게시판 프로젝트에 적용한다면 PR을 올릴 때 Gradle 빌드와 테스트를 실행할 수 있다. 메인 브랜치에 병합된 뒤에는 빌드한 Docker 이미지를 EC2에 전송하고 Compose로 앱 컨테이너를 교체한 다음, API가 정상 응답하는지 확인하는 절차를 구성할 수 있다. GitHub Actions에서는 PR 생성이나 푸시 같은 이벤트에 맞춰 이런 작업을 실행할 수 있다. [GitHub Actions 공식 문서](https://docs.github.com/en/actions/get-started/understand-github-actions)

## 2. HTTPS를 적용하는 이유

HTTPS는 HTTP 요청과 응답을 TLS로 보호하는 방식이다. 브라우저에서 게시판으로 보내는 글 내용이나 인증 정보처럼, 네트워크를 통해 오가는 데이터를 보호하는 데 사용한다.

| 보호 대상 | 의미 |
| --- | --- |
| 기밀성 | 전송 데이터를 암호화해 통신을 엿보는 사람이 내용을 읽기 어렵게 한다. |
| 무결성 | 전송 중 데이터가 변경되면 이를 감지할 수 있다. |
| 서버 인증 | 브라우저가 인증서의 도메인 이름과 신뢰 체인을 확인해 접속한 서버를 검증한다. |

이번 실습에서는 EC2의 Nginx가 443번 포트에서 HTTPS 요청을 받고, 같은 서버의 18080번 포트에 연결된 Nginx 컨테이너로 전달했다. 컨테이너 안의 Nginx는 Docker 내부 네트워크를 통해 Spring Boot의 8080번 포트로 요청을 보낸다. 일반 HTTP로 접속하면 HTTPS 주소로 이동한다. 이 구성에서 TLS로 보호되는 구간은 브라우저와 EC2의 Nginx 사이이다.

## 3. SSL과 TLS의 개념과 동작 방식

SSL과 TLS는 네트워크 통신을 보호하기 위한 프로토콜이다. TLS는 SSL의 후속 표준이다. 흔히 SSL 인증서라고 부르는 인증서도 HTTPS 연결에서는 서버가 TLS 연결을 맺을 때 사용한다.

### TLS 1.3 연결 과정

1. 브라우저가 지원하는 TLS 버전과 암호화 방식, 키 교환에 사용할 공개 정보를 서버에 보낸다.
2. 서버는 연결에 사용할 방식을 선택하고 자신의 키 교환 공개 정보를 보낸다. 이후 인증서와 서명을 보내 인증서에 대응하는 개인 키를 갖고 있음을 증명한다.
3. 브라우저는 인증서에 접속한 도메인이 포함되는지, 유효기간이 지났는지, 신뢰하는 인증기관으로 연결되는지 확인하고 서버의 서명을 검증한다.
4. 양쪽은 키 교환으로 얻은 공유 비밀에서 통신에 쓸 키를 만든다. 핸드셰이크가 끝나면 이 키를 사용한 대칭키 암호화로 HTTP 요청과 응답을 보호한다.

인증서와 서명은 서버의 신원을 확인하는 데 사용한다. 이후 게시글 목록과 같은 실제 데이터는 연결에서 만들어진 대칭키로 암호화해 주고받는다. [TLS 1.3 표준 문서](https://www.rfc-editor.org/rfc/rfc8446.html)
