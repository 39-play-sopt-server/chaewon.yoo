# 3주차 키워드 과제

## 1. Page와 Slice

Page와 Slice는 Spring Data에서 조회 결과를 일정한 크기로 나누어 반환할 때 사용하는 인터페이스이다. 두 방식 모두 조회한 데이터와 페이지 크기, 다음 페이지 존재 여부 등을 제공한다.

| 구분 | Page | Slice |
| --- | --- | --- |
| 전체 데이터 개수 | 제공한다. | 제공하지 않는다. |
| 전체 페이지 수 | 제공한다. | 제공하지 않는다. |
| 다음 페이지 여부 | 확인할 수 있다. | 확인할 수 있다. |
| 조회 비용 | 전체 개수를 구하는 COUNT 쿼리가 추가될 수 있다. | 일반적으로 요청 크기보다 한 개 더 조회해 다음 페이지를 판단한다. |
| 사용 상황 | 전체 페이지 수를 표시하는 페이지 번호 방식 | 더 보기나 무한스크롤 방식 |

Page는 전체 개수와 페이지 수가 필요한 목록에 적합하다. 다만 조건에 맞는 데이터가 많거나 JOIN이 복잡하면 COUNT 쿼리의 비용도 커질 수 있다. 전체 개수를 결과에서 알 수 있는 경우에는 COUNT 쿼리를 생략하기도 한다.

Slice는 전체 개수를 알 필요 없이 다음 데이터가 있는지만 확인하는 목록에 적합하다. 전체 개수를 구하는 비용은 줄일 수 있지만, 페이지 번호 기반의 Slice가 자동으로 커서 방식이 되는 것은 아니다. OFFSET이 커질 때 앞의 데이터를 건너뛰는 비용은 별도로 고려해야 한다.

페이지를 나눌 때는 정렬 기준이 필요하다. 생성일이 같은 데이터도 있을 수 있으므로 생성일과 고유한 ID를 함께 정렬 기준으로 사용하면 동일한 값 사이의 순서가 명확해진다. 다만 조회 사이에 데이터가 추가되거나 삭제되면 OFFSET 방식에서 중복이나 누락이 발생할 수 있다.


## 2. DB 인덱스의 개념과 활용

인덱스는 원하는 데이터를 찾는 데 사용하는 별도의 자료구조이다. 책의 찾아보기처럼 전체 데이터를 모두 확인하지 않고 필요한 위치를 찾도록 돕는다. 대표적으로 B-Tree 계열 구조가 사용된다.

| 장점 | 단점 |
| --- | --- |
| 조건에 맞는 데이터를 빠르게 찾을 수 있다. | 인덱스를 저장할 공간이 필요하다. |
| 정렬과 JOIN의 비용을 줄일 수 있다. | INSERT, UPDATE, DELETE 시 인덱스도 관리해야 한다. |

인덱스는 모든 컬럼에 추가하기보다 자주 실행되는 쿼리를 기준으로 정한다. WHERE 조건, JOIN 조건, ORDER BY에 사용하는 컬럼을 살펴보고 데이터의 분포와 변경 빈도도 고려한다. 중복이 적어 결과를 많이 좁힐 수 있는 컬럼은 유리할 수 있지만, 선택도가 낮다는 이유만으로 항상 효과가 없는 것은 아니다.

여러 컬럼을 묶은 복합 인덱스는 컬럼 순서가 중요하다. `(member_id, created_at)` 인덱스는 일반적으로 member_id 조건이나 두 컬럼을 함께 사용하는 쿼리에 활용하기 좋다. created_at만 사용하는 조회에는 같은 효과를 보장하지 않는다.

문자열 검색도 방식에 따라 다르다. 일반적인 B-Tree 인덱스는 `LIKE '검색어%'`와 같은 접두어 검색에 활용될 수 있지만, `LIKE '%검색어%'`의 범위를 효율적으로 좁히기는 어렵다. 전문 검색 인덱스를 사용할 수도 있지만 단어 분리와 검색 규칙이 달라 같은 결과를 보장하지 않는다.

인덱스를 만들었다고 반드시 사용되는 것은 아니다. DB가 판단한 비용에 따라 전체 조회가 선택될 수도 있으므로 EXPLAIN으로 실행 계획을 확인하고 실제 처리 시간도 비교해야 한다.


## 3. 회원 탈퇴 시 게시글 처리와 게시글·댓글의 생명주기

회원이 게시글을 100개 작성한 뒤 탈퇴하더라도 게시글의 처리 방식은 서비스 정책에 따라 달라진다. 회원을 삭제한다는 이유만으로 모든 게시글을 자동 삭제해야 하는 것은 아니다.

| 처리 방법 | 특징과 고려할 점 |
| --- | --- |
| 게시글도 삭제 | 탈퇴자의 글을 남기지 않는다. 연결된 댓글과 좋아요 등의 처리도 필요하다. |
| 게시글은 보존하고 작성자 연결 해제 | 글은 남기고 탈퇴한 회원으로 표시한다. 작성자 FK의 NULL 허용이 필요하다. |
| 회원을 소프트 삭제 | 삭제 표시를 남겨 회원 행과 관계를 유지한다. 개인정보 익명화와 탈퇴 회원의 접근 차단을 별도로 처리해야 한다. |
| 게시글이 있으면 탈퇴 제한 | 관계는 유지되지만 사용자가 글을 먼저 정리해야 하는 불편이 있다. |

게시판의 정보나 다른 사용자의 대화를 보존할 필요가 있다면 작성자 정보와 게시글의 생명주기를 분리할 수 있다. 이때 FK만 해제해도 본문에 개인정보가 남을 수 있으므로 개인정보 처리 범위는 별도로 판단해야 한다. 소프트 삭제 역시 개인정보의 실제 삭제와 같은 의미는 아니다.

게시글과 댓글의 관계는 회원과 게시글의 관계보다 종속적인 경우가 많다. 게시글은 작성자가 탈퇴해도 독립적인 정보로 남을 수 있지만 댓글은 특정 게시글의 대화라는 맥락에 의존한다. 그래서 게시글 삭제 시 댓글을 함께 삭제하는 정책이 자연스러울 수 있다.

다만 댓글이 달린 게시글은 내용만 삭제하고 행은 유지하거나, 대댓글의 대화 흐름을 위해 삭제된 댓글 자리를 남기는 정책도 가능하다. 생명주기는 단순히 연관관계가 있다는 이유로 결정하지 않고 독립적인 보존 가치와 서비스 정책을 기준으로 정해야 한다.

삭제와 연관 데이터 정리는 하나의 트랜잭션에서 처리할 필요가 있다. 데이터가 많으면 잠금 범위와 처리 시간도 고려해야 한다.

## 4. DB 무결성과 Cascade

무결성은 데이터가 정해진 규칙에 맞게 정확하고 일관된 상태를 유지하는 성질이다.

| 종류 | 의미 | 관련 제약 |
| --- | --- | --- |
| 개체 무결성 | 각 행을 유일하게 식별할 수 있다. | PRIMARY KEY의 중복과 NULL 금지 |
| 참조 무결성 | 참조하는 데이터 사이의 관계가 유효하다. | FOREIGN KEY |
| 도메인 무결성 | 값이 허용된 자료형과 범위를 따른다. | 자료형, NOT NULL, CHECK |
| 유일성 | 특정 값이나 값의 조합이 중복되지 않는다. | UNIQUE |

애플리케이션 검증은 사용자에게 오류를 설명하는 데 도움이 된다. DB 제약조건은 동시 요청이나 다른 프로그램의 접근에서도 규칙을 지키도록 한다. 두 역할은 함께 필요하다.

### DB의 Cascade

외래키의 ON DELETE, ON UPDATE는 부모 행이 삭제되거나 키가 변경될 때 참조하는 행을 어떻게 처리할지 정한다.

| 설정 | 동작 |
| --- | --- |
| CASCADE | 부모 삭제 시 자식도 삭제하거나 부모 키 변경을 자식 FK에 반영한다. |
| SET NULL | 자식 FK를 NULL로 바꾼다. 해당 컬럼은 NULL을 허용해야 한다. |
| RESTRICT / NO ACTION | 참조하는 자식이 있으면 부모 변경을 제한한다. MySQL InnoDB에서는 두 설정이 같은 방식으로 동작한다. |

### JPA의 Cascade

JPA의 CascadeType은 한 엔티티에 수행한 작업을 연관 엔티티로 전파하는 설정이다. DB의 외래키 동작과는 별개이다.

| 설정 | 전파하는 작업 |
| --- | --- |
| PERSIST | 저장 |
| MERGE | 상태 병합 |
| REMOVE | 삭제 |
| REFRESH | DB 상태로 다시 읽기 |
| DETACH | 영속성 컨텍스트에서 분리 |
| ALL | 위의 모든 작업 |

예를 들어 부모의 일대다 관계에 REMOVE를 지정하면 부모 엔티티 삭제가 자식에게 전파된다. orphanRemoval은 부모의 연관관계에서 빠진 자식을 삭제 대상으로 취급하는 설정이다. 부모와 생명주기를 함께하는 자식에 적합하다.

공유되는 회원처럼 독립적으로 존재하는 엔티티에는 삭제 전파를 신중하게 설정해야 한다. 게시글을 삭제할 때 작성자까지 삭제되면 그 회원이 작성한 다른 글에도 영향을 줄 수 있다. Cascade는 트랜잭션이나 무결성 제약을 대체하지 않는다.

DB에서 연쇄 삭제가 발생해도 이미 조회한 JPA 객체의 상태가 자동으로 모두 바뀌는 것은 아니다. 또한 JPQL 벌크 삭제는 일반적인 엔티티 삭제의 Cascade와 생명주기 콜백을 거치지 않으므로 처리 방식의 차이를 알아야 한다.
